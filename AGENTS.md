# execsql2

Maintained fork of [execsql](https://execsql.readthedocs.io/) v1.130.1 by R.Dreas Nielsen (upstream is unmaintained). A multi-DBMS SQL script processor: runs SQL scripts with metacommands (embedded in SQL comments) for import/export, cross-database copy, control flow, substitution variables, and interactive prompts against PostgreSQL, MySQL/MariaDB, SQLite, DuckDB, SQL Server, MS Access, Firebird, Oracle, and ODBC DSNs.

- Docs: <https://execsql2.readthedocs.io> · Repo: <https://github.com/geocoug/execsql>
- **Naming gotcha:** PyPI package is `execsql2`, the importable module is `execsql`, the CLI command is `execsql` (never write `execsql2` in CLI examples). Commands: `run` (implied when none is given — deprecated, removed in execsql2 3.0), `format`, `lint`, `config`, `list`, `init`, `lsp` (the language server editors start; `lsp` is therefore a reserved name for a bare script). The old `execsql-format` console script is gone; the pre-commit hook id `execsql-format` remains.
- `_execsql/execsql.py` is the vendored upstream monolith (16,627 lines) — **reference only, never edit**. Use it to learn what a script did upstream (see "Upstream is legacy"); `.agents/monolith_map.md` maps monolith sections to modern modules.
- Architecture deep-dive: `docs/dev/architecture.md`.

## Hard rules

- **Upstream is legacy** (decided 2026-10-18, replacing the same day's "Script compatibility" contract): execsql2 has feature parity with execsql v1.130.1, and upstream no longer constrains its design. A change may make an upstream script behave differently when that makes execsql2 better, provided the difference is deliberate and visible: the script corpus (`tests/corpus/`) flags every difference from upstream, and each one is listed in `tests/corpus/changes.json` as `accepted` with the reason, recorded in `docs/about/divergence.md`, and, if released behavior changes, in `CHANGELOG.md` with what to do differently. What still binds: the data-integrity decision below (IMPORT / EXPORT / COPY never silently change stored data), semver for execsql2's own releases (removing a metacommand, option or CLI form waits for 3.0; changed behavior ships in a minor release under `Changed`), and the maintainer's approval for any user-visible change. Use the monolith to learn what upstream did, not as a specification.
- **Changelog**: every user-visible change must be reflected in `CHANGELOG.md` under `[Unreleased]` in the same commit or PR, using [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) categories (Added, Changed, Fixed, Removed). Voice: terse, user-facing, one idea per bullet, naming the affected metacommand / flag / format / file. No root-cause prose, implementation details, test counts, coverage callouts, refactor notes, or docstring/typo fixes. Internal infrastructure work (CI, tests, refactors, renames) belongs in commit messages — if a release contains only internal work, collapse it to a single `Internal: …` line. Changelogs are for humans and explain what to do differently after upgrading.
- **Docs sync**: every user-visible change also updates documentation in the same change — `README.md`, `docs/`, and anything else that would go stale. New CLI options go in the full options reference (`docs/getting-started/syntax.md#options`); the README "Common options" table is a curated subset — add a flag there only if it is broadly useful. Docs quality over length: prioritize practical examples and useful detail over arbitrary brevity. Docs subdirectories: `docs/getting-started/`, `docs/reference/` (configuration, metacommands, substitution_vars, security), `docs/guides/`, `docs/about/`, `docs/api/`, `docs/dev/`.
- **Divergence record**: every change that diverges from upstream (new features, changed behavior, security fixes, removals) updates `docs/about/divergence.md` under its existing section headings. It is the canonical record of how execsql2 differs from the monolith.
- **Config template**: config option changes update `src/execsql/data/execsql.conf.template` (powers `execsql config --init`).
- **Metacommand registry**: new metacommands add `description=` and `category=` to the `mcl.add()` call in `metacommands/dispatch.py`, add a `metacommands/reference.py` entry (syntax forms as the docs write them, one-line summary, docs anchor) — `tests/test_reference.py` checks it against the dispatch table and the docs, and the LSP's completion/hover and `execsql list metacommands` read it — then run `just install-vscode` to regenerate the VS Code grammar. The dispatch table is the single source of truth for keywords (`execsql list keywords --output-format json` introspects it — `--dump-keywords` is its hidden alias; `tests/test_registry.py` validates consistency across dispatch table, CLI output, and grammar).
- **Coverage floor (two-tier)**: 85% cross-platform baseline (`--cov-fail-under=85` in `pyproject.toml`) plus 86% on the integration-tests CI job (live Postgres/MySQL/SQL Server containers). Local dev and macOS/Windows CI see ~85%; the canonical Ubuntu integration run sees ~86%. Only the vendored `_execsql/*` monolith is excluded from measurement. Path to 87%+: real Access tests on windows-latest (currently `continue-on-error: true`), Oracle XE / Firebird containers, GUI/exporter/CLI gap-fills.
- **Formatter corpus**: any change to `src/execsql/format.py` must pass the corpus checks over a library of *real* SQL, not only `tests/test_format.py`. Every formatter bug to date came from production SQL containing a construct the repo's own scripts lack. Run `EXECSQL_FORMAT_CORPUS=~/.cache/execsql-format-corpus uv run pytest tests/test_format.py -k corpus` (~100 s; that directory is a read-only copy of `~/GitHub/gsi/data-management/sql-library`, refreshed with `rsync -a --delete --include='*/' --include='*.sql' --exclude='*' ~/GitHub/gsi/data-management/sql-library/ ~/.cache/execsql-format-corpus/`). Never point the variable at the original library, and never copy client SQL into the repo — the in-repo corpus is every `.sql` file in the tree. A construct that broke the formatter gets a synthetic, non-client stand-in in `tests/data/formatter_shapes/`. sqlglot is pinned to one release (`[formatter]` extra, `.pre-commit-hooks.yaml`, `uv.lock`; `tests/test_tooling_versions.py` keeps them equal; Dependabot ignores it) because its output changes between releases (#72): bump all three together and run the corpus.
- **Quality gates**: all code passes `ruff check`, `ruff format`, and `mypy src/execsql/` with zero errors (gated in CI and pre-commit). Target Python 3.10+ — 3.10 support is maintained for the foreseeable future; never propose dropping it.
- **Release monitoring**: after every version bump, push with `git push && git push --tags`, then `gh run list --limit 1` for the run ID and `gh run watch <id> --exit-status` until completion. Bump tags trigger PyPI publish and GitHub Release — failures must be caught and fixed immediately. `docs/dev/releasing.md` is the one release checklist (jobs, release notes, recovery).
- **No destructive git operations** without human approval.
- **No silent scope reduction**: phrases like "v1", "placeholder for now", "will wire later", "simplified version" are prohibited. If full scope doesn't fit in one task, propose a phase split — never ship half-finished work.
- The auto-docs post-tool hook in `.claude/settings.json` operates independently — don't disable it. The auto-changelog hook was removed on 2026-08-28: it invoked an `/update-changelog` skill that was never installed, so it no-op'd on every edit while appearing to enforce the changelog rule. The changelog rule above still stands and is now enforced by hand.

## Layout

`src/execsql/`: `cli/` (Typer entry, DSN parsing, run loop) · `db/` (Database ABC, 9 adapters, `factory.py` constructors) · `exporters/` + `importers/` (format I/O) · `metacommands/` (`dispatch.py` registrations, `x_*` handlers, `conditions.py` predicates) · `script/` (AST engine, variables) · `gui/` (tkinter / textual / console backends) · `utils/` · `state.py` (module-level runtime state via thread-local proxy) · `types.py` / `models.py` (type system) · `format.py` (`execsql format`) · `lsp/` (`execsql lsp`, pygls 2: one module per LSP feature; reuses `cli.lint`, `format`, `metacommands.reference` and `cli.run._tool_config`; settings per workspace folder) · `metacommands/reference.py` (human-readable syntax registry beside the regex dispatch table).

Optional extras (see pyproject.toml): drivers `postgres` (psycopg3), `mysql`, `mssql`, `duckdb`, `firebird`, `oracle`, `odbc`; bundles `formats`, `auth`, `auth-plaintext`, `auth-encrypted`, `upsert`, `map`, `formatter`, `lsp` (pygls + lsprotocol + the formatter); groups `all-db`, `all`. Dev tools are the `dev` and `docs` dependency groups (`[dependency-groups]`, unpublished). The VS Code extension lives in `extras/vscode-execsql/` (not shipped in the wheel; each GitHub Release attaches it as `execsql-syntax.vsix`; local install via `just install-vscode`). It starts `execsql lsp` only in a trusted workspace and resolves `execsql` through PATH, never from the open folder.

## Decisions

- Install path is `uv tool install execsql2` / `pipx install execsql2` — no zipapp or wrapper artifacts.
- Some roadmap context lives in Claude's persistent memory, which Codex cannot read. GitHub issues are the shared source for roadmap and backlog; do not migrate private memory automatically.
- Release notes (decided 2026-10-14): each GitHub Release body is that version's `CHANGELOG.md` section, not GitHub's generated commit list. `docs/dev/releasing.md` is the one release checklist; CONTRIBUTING and this file link to it.
- Docs default version (decided 2026-10-14): Read the Docs serves `stable` (the newest release tag) by default; `latest` (main) stays reachable for unreleased docs. Docs links point at `/en/stable/`.
- VS Code extension version (decided 2026-10-14): `extras/vscode-execsql/package.json` carries the package version, bumped by bump-my-version with the rest; CI checks it equals the tag instead of rewriting it.
- Dev tooling (decided 2026-10-14): test, lint and docs tools live in `[dependency-groups]` (unpublished; a `docs` group shared by Read the Docs and CI), not in a published `dev` extra. Extras are only for user-facing features.
- CI guards: add one only for a failure that happened, or one that would be costly and late (a failed publish on a tag); the uv/twine pin guards and the duplicate formatter-corpus job were removed on 2026-10-14 for this reason.
- Time zone names in imported timestamps (decided 2026-10-15): only UTC/GMT/Z and numeric offsets are read as zones; any other name (EST, PST, …) makes the value text. No abbreviation map: abbreviations are ambiguous and the result must not depend on the host's zone.
- pyodbc connection pooling (decided 2026-10-16): off. The SQL Server, Access and DSN adapters set `pyodbc.pooling = False` before connecting, so every `CONNECT` and `execsql.run()` is a new session (unixODBC handed pooled sessions back with their temp tables and `SET` options). Process-wide and documented; no config option, because pyodbc applies it only at the process's first connection.
- Data integrity in IMPORT / EXPORT / COPY (decided 2026-10-16, critical): never change or mangle data. A change to how values are converted, inserted or written must store exactly what the old code stored, proven by a differential test over every value type × column type (and the error cases); speed never justifies a different stored value. PostgreSQL `COPY FROM STDIN` was dropped from PR #95 for this reason (37 silent differences).
- Loads into an existing table (decided 2026-10-17, issue #100): `IMPORT` / `COPY` into a table that already exists convert each value by the target column's type, not by the type scanned from the source; a text column gets the source value as written. A value with a fraction going into an integer column is an error, never rounded. `TO NEW` / `TO REPLACEMENT` still create and fill the table from the scan. `tests/db/test_existing_table_loads.py` holds the before/after record (`tests/data/existing_table_loads/`).
- Conditions that cannot be evaluated (decided 2026-10-19, issue #112): an `IF`, `ELSEIF`, `ANDIF`, `ORIF` or `LOOP` condition that raises stops the run, whatever `METACOMMAND_ERROR_HALT` says. Upstream carried on past a bad inline `IF` (and ran both branches of a block `IF`); a bad condition is a script bug, and making it a metacommand error would also hide database errors raised inside conditions (`HASROWS`, `TABLE_EXISTS`).
- Control flow from a substitution variable (decided 2026-10-19, issue #113): `-- !x! !!cmd!!` holding an `INCLUDE`, `EXECUTE SCRIPT`, `IF` or other block metacommand fails with an error instead of running; upstream ran it. The stubs' wording, and a block `IF` / `LOOP` added with `EXTEND SCRIPT … WITH METACOMMAND` (upstream runs it), are open in #119. Not implemented because the maintainer has no use for it and run-time re-classification of every metacommand kept leaking gaps in #111. `INCLUDE !!file!!` / `EXECUTE SCRIPT !!name!!` / `IF (!!cond!!)` are the supported forms.
- Batches left early (decided 2026-10-21, issue #121): a `BEGIN BATCH` block is committed only at `END BATCH`. `BREAK`, an error or `HALT` rolls it back; `exit_now` does so before an `ON ERROR_HALT` / `ON CANCEL_HALT` script runs, so that script's SQL commits. A nested batch left while the outer batch carries on hands its statements to the outer batch (maintainer's choice), and under `AUTOCOMMIT OFF` nothing is rolled back, mirroring `END BATCH`, which commits nothing there.
- DISCONNECT (decided 2026-10-22, issue #124): `DISCONNECT FROM` an alias that is not connected is a metacommand error, worded like `USE`'s ("Unrecognized database alias: x."); aliases match in any case; a database an open batch has used is refused.
- Batch rules (decided 2026-10-22, issue #125, "model A"): a batch commits at `END BATCH` only if nothing in it failed. (1) If anything in a batch fails — an SQL statement, a metacommand, or a metacommand's SQL — that batch and every batch around it are not committed. Marked in one place, `_fail_open_batches()`, called by `_sql_failed()` and `_metacommand_failed()` (decided after PR #131's third review: marking at each database rollback site kept missing paths, such as Access, PG_UPSERT and a failed BEGIN). (2) A failed batch is rolled back at `END BATCH`, which reports an SQL error that `ERROR_HALT` governs; `END BATCH` clears `SQL_ERROR()` first, so right after it `SQL_ERROR()` says whether the batch was committed; `ROLLBACK BATCH` does not undo the failure (no recovery). A failed `END BATCH` commit rolls back the databases not yet committed and fails the enclosing batches. (3) `BREAK`, an error or `HALT` rolls the batch back (#121). (4) Where nothing can be held back the batch promises nothing, and the docs say so: `AUTOCOMMIT OFF` (END BATCH still reports the failure; the script's transaction is left to it), a driver that commits every statement, and `IMPORT` / `COPY` / `EXECUTE` / `AUTOCOMMIT ON WITH COMMIT`, which commit on their own. (5) Outside a batch, a failed commit must not leave work pending (#135, open). Savepoint-per-statement (psql's ON_ERROR_ROLLBACK) was considered and not chosen.
- Interrupted statements (decided 2026-10-22, issue #139): an SQL statement or metacommand that an interrupt (a BaseException other than execsql's control flow, `_CONTROL_FLOW`: `ScriptExit`, the `SystemExit` subclass raised by `exit_now()` (HALT, halting errors, cancelled PROMPT), cancelled dialogs and `.quit` / `.abort`, and `_BreakLoop` from BREAK; a plain `SystemExit` — execsql's SIGTERM handler, a host's signal handler, quitting the Textual console — is an interrupt. Decided 2026-10-26 after #140's third review: telling them apart by `SystemExit` alone failed both ways) stops is treated as a failed one: `_record_interrupt()` fails the open batches and sets `SQL_ERROR()` / `METACOMMAND_ERROR()`, `$LAST_ERROR`, `$ERROR_MESSAGE` ("Interrupted."), without halting. `_exec_sql` then rolls back its connection whatever AUTOCOMMIT says (as `Database.execute()` does on an error); `_exec_metacommand` rolls back every connection with autocommit on and leaves AUTOCOMMIT OFF to the script. That rollback takes the metacommand's own writes and whatever else is pending there: a batch's earlier statements, or work held under AUTOCOMMIT OFF that a plain `AUTOCOMMIT ON` left for the next commit (confirmed 2026-10-27 in #149: an interrupted SQL statement rolls that back too, and a shared connection cannot roll back the metacommand's writes alone). An interrupt that lands after the driver has committed cannot undo the commit. Chosen over a `run()`-level rollback, which missed the BREAKPOINT prompt (it carries on after Ctrl-C) and needed rules of its own for AUTOCOMMIT OFF and connections opened with CONNECT. A batch leaves its stack only through END BATCH's commit or by being abandoned, so an interrupt anywhere up to the commit rolls it back (#150). Backstop (decided 2026-10-28 in #150, after interrupt handling drew review findings in #140, #149 and #150): an interrupt can land between any two lines of Python, such as between the rollbacks of a batch's databases, so an interrupt that ends `execsql.run()`, or the input typed at a BREAKPOINT prompt (`execute_input`; the run carries on there), also rolls back every connection with autocommit on (`_roll_back_after_interrupt` in the executor); AUTOCOMMIT OFF connections stay the script's. Do not chase the remaining one-line windows site by site.
